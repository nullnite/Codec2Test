# Codec2 over LoRa on RAK4630 — Development Log

## Overview

A complete LoRa voice communication system was built on two RAK4630 modules
(nRF52840 + SX1262) using PlatformIO with the Arduino framework. The goal was
to encode speech using Codec2 MODE_2400 on one device, transmit it over LoRa,
and decode it on the other device.

---

## Codec2 Port

### Source File Curation

The raw codec2 repository cannot be dropped into `lib/codec2/` directly — it
compiles everything including test harnesses, simulation tools, FreeDV modem
code, and FDMDV files that were never intended for embedded targets. Instead,
only the files required for MODE_2400 were manually copied:

**Core codec:**

- `codec2.c`, `lpc.c`, `lsp.c`, `nlp.c`, `postfilter.c`, `sine.c`,
  `phase.c`, `quantise.c`, `interp.c`, `pack.c`, `mbest.c`

**FFT:**

- `codec2_fft.c`, `kiss_fft.c`, `kiss_fftr.c`

**Codebooks (MODE_2400 only):**

- `codebook.c`, `codebookd.c`, `codebookge.c`, `codebookjmv.c`

### Codebook Generation

The codebook `.c` files do not exist in the repository as source — they are
generated at build time by a host-side `generate_codebook` executable compiled
from the codec2 CMake system. Each file was generated from the corresponding
`.txt` files in `codec2/codebook/`:

```bash
src/generate_codebook lsp_cb lsp1.txt ... lsp10.txt > codebook.c
src/generate_codebook ge_cb gecb.txt > codebookge.c
src/generate_codebook lsp_cbd dlsp1.txt ... dlsp10.txt > codebookd.c
src/generate_codebook lsp_cbjmv lspjmv1.txt lspjmv2.txt lspjmv3.txt > codebookjmv.c
```

### `version.h` Fix

The codec2 `version.h` is normally generated by CMake from a `.in` template.
The file that ends up in a manual copy is a cmake-generated desktop file that,
when included with angle brackets (`<version.h>`), resolves to the C++ standard
library `<version>` header on ARM GCC. This pulls in C++ runtime static
initializers that run before the SoftDevice and USB peripheral are ready,
corrupting startup and preventing USB serial from enumerating. The fix was to
replace it with a minimal hand-written file:

```c
#ifndef CODEC2_VERSION_H
#define CODEC2_VERSION_H
#define CODEC2_VERSION_MAJOR 1
#define CODEC2_VERSION_MINOR 2
#define CODEC2_VERSION_PATCH 0
#define CODEC2_VERSION "1.2.0"
#endif
```

### CMSIS-DSP Acceleration

codec2 has a built-in ARM CMSIS-DSP path controlled by the `FDV_ARM_MATH`
define. When enabled, `codec2_fft.c` uses `arm_cfft_f32` and
`arm_rfft_fast_f32` instead of KISS FFT. Enabling this required:

1. Downloading `libarm_cortexM4lf_math.a` from the
   [CMSIS 5.7.0 release](https://github.com/ARM-software/CMSIS_5/tree/5.7.0/CMSIS/DSP/Lib/GCC)
2. Adding to `platformio.ini`:

```ini
build_flags =
    -DFDV_ARM_MATH
    -DARM_MATH_CM4
    -l arm_cortexM4lf_math
```

This reduced encode time from ~35ms/frame to ~16ms/frame.

## FreeRTOS Stack Requirements

Both `codec2_encode` and `codec2_decode` require large stack frames internally.
`nlp_create` alone needs ~6–8KB for its FFT working buffers. Running these
functions on the default Arduino loop task (2KB stack) causes an immediate
hardfault and reboot with no error message.

The fix is to run all codec2 operations on dedicated FreeRTOS tasks with
adequate stack:

```cpp
xTaskCreate(codec2_init_task,   "c2init",  4096, NULL, 1, NULL); // 16KB
xTaskCreate(codec2_encode_task, "c2enc",   4096, NULL, 1, NULL);
xTaskCreate(codec2_decode_task, "c2dec",   4096, NULL, 1, NULL);
```

The Arduino loop task stack size is separate and controlled by the BSP.

## Performance

| Operation          | Time per frame | Real-time ratio |
| ------------------ | -------------- | --------------- |
| Encode (CMSIS-DSP) | ~16ms          | 0.80×           |
| Decode (CMSIS-DSP) | ~31ms          | 1.55×           |

Profiling showed that 87% of decode time is spent in `aks_to_M2`, which
performs a 512-point real FFT (`arm_rfft_fast_f32`) twice per 20ms frame.

## TX Pipeline

The transmitter uses a double-buffer pipeline to overlap encoding with
transmission:

```
Buffer 0: [encode] → [transmit ~67ms airtime]
Buffer 1:            [encode next packet]
```

- **Mode:** Codec2 MODE_2400
- **Frames per packet:** 4 × 6 bytes = 24 bytes payload
- **LoRa config:** SF7, BW125, CR 4/5, 868MHz, 22dBm
- **TX cycle:** ~76ms
- **Encode time for 4 frames:** ~71ms (overlapped with TX)

---

## RX Pipeline

```
OnRxDone → raw_pkt_q → decode_task → pcm_out_q → serial_output_task
```

- `OnRxDone` copies the payload and immediately re-arms `Radio.Rx()`
- `decode_task` pulls raw packets and calls `codec2_decode` for each frame
- `serial_output_task` sends decoded PCM over USB serial with framing

### Serial Framing Protocol

Each decoded frame is sent with a 6-byte header:

| Byte | Value  | Description                    |
| ---- | ------ | ------------------------------ |
| 0    | `0xFF` | Marker byte 1                  |
| 1    | `0xFE` | Marker byte 2                  |
| 2    | `seq`  | Sequence number (wraps 0–255)  |
| 3    | `0x40` | Length low byte (320 = 0x0140) |
| 4    | `0x01` | Length high byte               |
| 5    | `chk`  | XOR checksum of payload        |

Followed by 320 bytes of raw 16-bit signed PCM at 8000Hz mono.

---

## Fundamental Limitation

Decode takes 31ms/frame × 4 frames = **124ms per packet**, but packets arrive
every **76ms**. The decode queue fills faster than it drains, dropping ~40% of
packets in real-time operation.

By making the raw packet queue large enough (300 entries) to buffer an entire
transmission, the system can decode non-real-time with no packet loss. Audio
quality verified by ear matches a PC reference decode using `c2dec`.
